## 2. 27.0 使用的关键对象偏移

单位：字节，相对各自的基址。`basePtr = p + BlockOff`、`person = p + PersonOff`、`db = p + DbOff`，
其中 `p` 是扫描命中 vtable 的位置（上游 `MemScan.Classify` 给出三者）。

### 2.1 对象头与动态偏移

| 字段 | 偏移 | 说明 |
| --- | --- | --- |
| `OBJ_DUNI` | `0x0C` | 对象唯一 ID（u32），相对 `db` |

## 3. 版本识别逻辑

现状有四处，彼此独立：

1. **上游 `Fields.ForVersion(major)`**：`27 → FM27`，其他 → `null`。只看**主版本**，因此 27.1 会拿到 27.0 的
   `Fields.FM27`；上游同时用 `versionOk`（major.minor 与 `SupportedVersion` 相等）自检，27.1 时为 `false`，
   但仍会继续读（只给 web 端一个警告）。
2. **读取器 `CompatibilityService` + `config/compatibility.json`**：按 `AppId + Build + PluginVersion` 查表，
   只有 `verified` 才允许进入 `Compatible`；`candidate` 一律 `Unknown` 并拒绝 probe/scan。
3. **读取器 `PluginProbe` / `SteamLocator`**：找安装目录、读 `game_plugin.dll` 文件版本、读 `appmanifest` 的
   `buildid`。
4. **ScoutMind 引擎 `VersionGate`（`verified-versions.json`）**：按构建号 + 插件主次版本放行；27.1 构建
   `26620374` 标为 `candidate`。

新增的 `LayoutResolver` 与 `CompatibilityRegistry` 是第五、第六处：前者把构建号映射到 `FM27_0` / `FM27_1`，
后者记录“该构建的哪些字段已被真实核对”。三者（读取器清单、引擎闸门、注册表）都必须放行才会读内存。

## 4. Probe 验证逻辑

改造前：`probe` 只做版本闸门 + 打开进程，**不验证任何字段**——这也是本次要补的短板。

改造后（`FMSuperScoutMemoryEngine.DiagnoseAsync`）：

1. 识别构建 → `LayoutResolver` 取布局（未登记即停）；
2. 用上游分类器在堆里定位样本：球员最多 64 个、俱乐部最多 16 个，均带时间预算；
3. 依次执行 7 组探测：

| 探测 | 检查内容 |
| --- | --- |
| `player` | CA/PA 1..200、CA≤PA、身高 0 或 140..230、出生年份 1940..2015、姓名可打印、15 个位置字节 ≤20、属性块前 20 字节 ≤100、个人块在模块内、合同指针可读 |
| `club` | 名称可读、球队向量 `[begin,end)` 合理 |
| `team` | 合同→球队→俱乐部链可达、`teamType` 0..20、球队球员向量合理、**球员确实出现在自己球队向量里**（跨字段） |
| `contract` | 指针可读、到期日可解码且在 2000..2060、周薪上限、状态位不是 0xFF、到期日晚于出生 14 年且不超 45 年 |
| `loan` | 布局无租借偏移 → 明确 `NotApplicable`（不伪造通过） |
| `transfer` | 哨兵双命中、状态字节、双方球队指针、日期可解码 |
| `integrity` | 样本量 ≥20、`OBJ_DUNI` 唯一、姓名基本唯一、可读率、至少 1 个俱乐部 |

4. `ReportBuilder` 汇总为 `Verified / Candidate / Rejected / Unknown`。只有**全部必填字段 Verified 且所有适用探测
   Passed** 才是 `Verified`；任何探测 Failed 或字段 Rejected → `Rejected`；结构通过但字段未核对 → `Candidate`。

判定原则：**单一数值合理不算成功**。每个探测都是“多字段 + 关系 + 跨字段”的组合，且明确说明结构自洽不能
证明数值正确。

## 5. 当前无法验证的字段

| 类别 | 字段/能力 | 为什么无法验证 |
| --- | --- | --- |
| 租借与所有权 | 无任何 `loan/parent` 偏移 | 上游布局里不存在；只能来自阵容 CSV |
| 转会金额 | `DEAL_*` 无 amount 字段（上游明确说 `+0x20` 常等于身价，不可靠） | 数据本身不可信，ScoutMind 不用 |
| 阵容层级 | `TEAM_TYPE` 的整数语义来自上游注释 | 需要在游戏内对照预备队/青年队确认 |
| 士气/状态 | `PLAO_MORALE` / `PLAO_CONDITION` 的含义与范围 | 上游未在 27.0/27.1 逐项核对；当前不映射 |
| 隐藏性格 | `PERO_*` 性格字节 | 上游标注为“隐藏属性”，未纳入协议 |
| 联赛/级别 | `TEAM_COMP` 指针链 | 上游只在 FM26 上钉过，27.x 未复核 |
| 27.1 的全部字段 | 整张表 | 上游按 27.0 钉的，27.1 未核对 |

## 6. 27.1 适配所需修改清单

已完成（本次）：

1. `Layouts/FM27_0_Layout.cs`、`FM27_1_Layout.cs`：两份独立布局；
2. `Layouts/LayoutResolver.cs`：构建号 → 布局（未登记 → `null`）；
3. `Versioning/CompatibilityRegistry.cs` + `compatibility-registry.json`：构建 → 布局 + 已验证字段 + 证据；
4. `Engine/GameBuildDetector.cs`：进程/安装目录/插件/构建号识别（含 Steam 库在非系统盘）；
5. `Probes/`：内存源抽象、对象定位、7 组探测、字段校验（范围/指针/关系/跨字段）、报告生成；
6. 引擎：`DiagnoseAsync` 新入口，`ProbeAsync` 返回报告，`ScanAsync` 增加注册表 + 布局双重闸门；
7. 诊断工具：`report`、`layout` 子命令。

仍需人工完成（Phase 6 的前置）：

8. 在**加载了存档**的 FM27 27.1 上运行 `report`，确认 `player` 探测通过（证明布局没有明显错位）；
9. 逐类对照游戏内界面核对 CA/PA、身高、惯用脚、合同到期/周薪、俱乐部名称、球队层级，把结果写进
   `compatibility-registry.json` 的 `verified_fields` 与 `layout` 的 `Mark(...)`；
10. 把 `verified-versions.json` 与 `config/compatibility.json` 的对应条目改为 `verified`；
11. 重跑 `scan`，用真实存档做回归（两次扫描 id/CA/PA/合同一致）。

在 8–11 完成之前，27.1 的正式扫描保持禁止——这是设计，不是缺陷。
