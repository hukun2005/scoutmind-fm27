# V3.2.9 性能与批处理报告

## 1. 设计约束

| 约束 | 实现 |
| --- | --- |
| 有界内存 | 只加载 id / player_id / UID / 姓名 / 生日元数据；不加载原始内存、不缓存转储 |
| 有界批 | 默认 200，最大 1000；每批一次 `commit` |
| 可恢复 | 游标 + 作用域校验；不匹配立即 Failed |
| 单行失败隔离 | 单条异常只累加 `failed_count`，不中断整批 |
| 幂等 | `scan_id` 唯一；观测 `observation_key` 唯一；审核条目 `item_key` 唯一 |

## 2. 本地实测（内存 SQLite，非游戏环境）

命令：临时基准脚本，构造 1200 个球员实体与实例，`batch_size=200`。

| 指标 | 结果 |
| --- | --- |
| 状态 | Completed |
| 处理行数 | 1200 |
| 匹配 | 1200 |
| 冲突 | 0 |
| 首次扫描耗时 | 1.496 s |
| 第二次扫描耗时 | 1.265 s |
| 每行耗时 | 1.246 ms |
| 吞吐 | 802 行/秒 |

说明：这是内存 SQLite 的上限参考，不是真实存档或 PostgreSQL 的承诺值。真实环境（磁盘 + PostgreSQL + 更大球员量）应更慢，必须重新测量。

## 4. 已知风险

1. `_build_index` 会把一个存档的全部身份元数据装入内存；上限 `MAX_INDEXED_INSTANCES = 200000`，超过直接拒绝而不是 OOM。
2. 每批都会重算重复 UID 分组；在极端重复率下会增加批耗时，但仍是存档内有界查询。
3. 扫描期间新增实例会触发 `BATCH_CHECKSUM_MISMATCH`，需要在新 `scan_id` 下重新扫描；这是刻意选择，避免把旧进度应用到变化后的数据。
