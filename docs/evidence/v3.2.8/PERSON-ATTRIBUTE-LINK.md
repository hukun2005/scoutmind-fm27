# Phase 4：Person → 球员属性记录关联（真实内存，只读）

> 运行日期：2026-11-25 · 游戏：FM27 27.1 · 构建 26620374 · 插件 27.1 · 进程 pid 72012
> 证据文件：`person-attribute-link-audit-2026-11-25.json`、`person-attribute-link-sample-2026-11-25.json`

## 1. 目标与边界

- 目标是建立 Person 对象与现有球员属性记录之间**可信、可审计**的关联。
- 全部读取只经只读内存接口：不写内存、不改保护属性、不注入 DLL、不修改存档。
- 姓名匹配只能产生候选关联；多个候选时禁止自动取第一个。
- 本阶段不执行 Mark(Verified)；关联结果中的 `VerifiedMatch` 仅在调用方显式传入人工确认标记时出现，本次真实运行未传入。

## 2. 关联字段与优先级

实现按任务书 6.1 的顺序使用已确认可读的字段：

| 优先级 | 字段 | 本次真实运行可用性 |
| --- | --- | --- |
| 1 | UID（DB 块 `OBJ_DUNI`） | 60/60 可读且非 0/非哨兵 |
| 2 | 出生日期（`PERO_DOB`，FM 日期） | 60/60 可读 |
| 3 | 姓名（`PERO_FIRST_NAME` / `PERO_SECOND_NAME` / `PERO_COMMON_NAME`） | 48/60 可读；12 条姓名槽为 0 |
| 4 | 俱乐部（合同 → 球队 → 俱乐部名称链） | 43/60 可读；17 条无可解析合同链 |
| 5 | CA / PA（`PLAO_CA` / `PLAO_PA`） | 可读，仅作为证据记录，不参与身份判定 |

缺失字段一律保持 `null` 并记入 `missing_fields`，不默认为 0，也不作为"匹配成功"。

## 3. 关联算法（路线 A）

1. 从目标 Person 读取身份字段：姓名、出生日期、俱乐部、UID。
2. 对每条属性记录逐字段比较，得到 `applicable` / `matched`：
   - 姓名：双方都有完整姓名时比较归一化后的完整组合（忽略大小写、重音、多余空白）；只有单侧姓名时不参与比较。
   - 出生日期：双方都有值时才比较。
   - 俱乐部 / UID：双方都有值时才比较。
3. **强匹配**只能来自姓名或 UID；生日单独命中不足以建立关联。
4. 存在任一可比较字段不一致的候选被排除；若其姓名已匹配，则作为**冲突证据**单独保留。
5. 结果状态：
   - `NoMatch`：没有候选。
   - `SingleCandidate`：唯一候选，未人工确认。
   - `MultipleCandidates`：多个候选，全部保留，不自动选择。
   - `ConflictingIdentity`：存在同名但其它字段冲突的记录。
   - `VerifiedMatch`：唯一匹配且调用方显式确认人工核对（本次未触发）。
   - `RejectedMatch`：目标本身没有姓名也没有 UID，无法关联。

### 同名球员处理规则

- 姓名键只使用"名 + 姓"的完整组合（以及常用名）；**不**把单个词作为姓名键。
  - 这条规则来自真实运行中的一次纠偏：早期版本把 "Ahmed" 单独作为姓名键，导致 `Ahmed Rashid` 与 `Ahmed Al-Hosani` 等 9 条同名不同人的记录被误判为冲突；修正后该目标恢复为 `SingleCandidate`。
- 同名同生日但 UID 不同、或同名但生日/俱乐部不同，都会产生 `ConflictingIdentity` 并保留证据。
- 同名同生日且 UID 相同（真实重复记录）会产生 `MultipleCandidates`，等待人工处理。

## 5. 限制

- 本次存档中 17/60 条记录无法走通合同 → 球队 → 俱乐部链，俱乐部字段缺失；因此这部分的俱乐部交叉校验未生效，报告中如实标记为缺失。
- 12/60 条记录姓名为空，只能依靠 UID + 出生日期建立关联；这些记录不满足 Phase 5 的"姓名成功读取"前置条件。
- 抽样规模为 60/800，不能外推为"全库无重名"；只说明本次抽样范围内唯一。
- CA/PA 在游戏界面不可见，本阶段只作为证据记录，不用于身份判定，也不据此声明数值已验证。
- 本次没有人工在 FM27 界面逐项核对，未执行 Mark(Verified)，所有候选仍停留在未验证状态。
