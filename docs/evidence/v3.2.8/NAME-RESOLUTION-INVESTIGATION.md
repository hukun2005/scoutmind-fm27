# V3.2.8 姓名解析调查（路线 A 阻塞分析）

- 执行日期：2026-11-25
- 内存操作：全部只读（`ReadProcessMemory`）。未写内存、未改存档、未注入、未改 DLL。
- 脱敏：不记录本机绝对路径与真实内存地址。

## 1. 目标

判断能否从当前 `26620374 / 27.1` 的属性记录出发，通过直接字段、指针链路或索引，可靠解析球员姓名。

## 2. 已确认事实

| ID | 事实 | 证据 |
| --- | --- | --- |
| N1 | `+0x50/+0x58/+0x60` 姓名槽指针恒为 0 | `probe` 姓名 0/32；`calibrate` 60 对象；`dump` 5 条样本 |
| N2 | `0x0..0x400` 全偏移扫描无任何姓名命中 | `calibrate 60 1024`，`name_like=0` |
| N3 | 记录内没有内联 ASCII 姓名 | `dump` 968 字节内仅 3～4 段零散字节串 |
| N4 | 真实姓名位于独立的“姓名池”对象（每 8 字节指向一个 wrapper，字符串在 inner+4） | `manual-e/calibration-notes.json` F1/F3 |
| N5 | 记录与姓名池之间无直接/两级指针链路（全内存反查 0 命中） | `manual-e` F4；`trace_name.py` |
| N6 | 把记录内整数当姓名池下标的假设自相矛盾 | `manual-e` F6；`index_hypothesis.py` |
| N7 | `+0x118/+0x120/+0x128` 的 `0x076C0001` 对所有球员相同，**不是** per-player 索引 | 本次 5 条样本（CA 81/103/…，生日 2001–2008）全部相同 |

## 3. 本轮新增实验

对 5 个不同球员对象（CA 与生日均不同）读取同一组偏移：

```
+0x118 = 0x076C0001076C0001
+0x120 = 0x076C0001076C0001
+0x128 = 0x076C0001076C0001
```

字段值完全相同，且与生日/CA 无关。

结论：此前怀疑“记录内重复整数是姓名池索引”的线索（F5）被否定——这些字段是常量/标志位，
不能用来区分球员，也不指向姓名池。

## 4. 结论

| 项目 | 状态 |
| --- | --- |
| 姓名直接字段（`0x50/0x58/0x60`） | FAIL |
| 姓名指针链路（一跳/两跳） | FAIL（0 命中） |
| 记录内整数 → 姓名池下标 | FAIL（常量，非索引） |
| 姓名解析机制 | UNKNOWN |
| 路线 A（Person 直接带姓名） | 当前构建下不可行 |

当前构建的姓名存储模型与 27.0 不同（27.0 的 `PERO_COMMON_NAME` 等偏移在此构建无效）。
在取得新的可靠证据前：

- 不修改 `FM27_0/FM27_1` 的生产偏移常量。
- 不把任何姓名候选标为 `Verified`。
- 真实运行中 `PersonCandidateLocator` 返回 `NameNotFound` 是正确行为。

## 5. 后续建议

1. **优先**：由用户在游戏界面提供 2～3 名球员的姓名/生日/俱乐部，作为真实锚点，做定向比对。
2. 用锚点回溯“姓名池”对象，确认其是否为全局字符串表，以及是否存在稳定的外部索引（路线 B 可行性）。
3. 若仍无法建立关联，V3.2.8 的姓名级能力保持 `NOT_RUN`，不以其它能力评分替代 CA，也不以姓名匹配推断身份。
4. 不建议在无锚点情况下做全内存 UID/哈希索引重构（任务书 §10 明确本阶段不提前重构）。

## 6. 更正（同日，锚点复核后）

用户随后提供了两名真实球员截图。按生日 u32 + 身高定位记录后，`nested_string` 直接在
`+0x50/+0x58/+0x60` 解出了正确姓名（`Dominic` / `Calvert-Lewin`、`Ethan` / `Ampadu`）。

因此：

- 本文 N1/N2 的“姓名直接字段 FAIL”结论**撤回**：偏移正确，`0/32` 是 `FindPlayers` 前 N 个采样的偏差。
- N3–N7 仍然成立（记录内无内联姓名、无指针直达姓名池、`0x076C0001` 非 per-player 索引）。
- 路线 A 在姓名层面**可行**；不需要先做路线 B 的姓名池索引。

详见 `REAL-ANCHOR-VERIFICATION.md`。
