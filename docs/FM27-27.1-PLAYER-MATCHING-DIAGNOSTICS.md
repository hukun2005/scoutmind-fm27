# 未匹配记录诊断（FM27 27.1 · 400 抽样 / 33 条未匹配）

本文件回答一个问题：**为什么 400 条抽样里有 33 条没配上？** 结论只分类、不删除、不强行配对。

- 生成时间：2026-11-19
- 环境：Steam Build `26620374`、FM `27.1.0`、`game_plugin.dll 27.1`、ScoutMind 读取器 `FM27_1` 布局（`Pending`）
- 参照数据：`exports/real-dump-20261118/dump.json`（FMSuperScout 1.7.3 读出的同一存档，48,089 名球员，按「姓名+出生年」唯一键 47,950 条）
- 复现命令：

```powershell
.\live-reader\tools\ScoutMind.FMReader.Diag\bin\Release\net10.0\ScoutMind.FMReader.Diag.exe `
  match .\exports\real-dump-20261118\dump.json 400
```

## 1. 结论（一句话）

**33 条全部是"一侧不存在对应记录"**：它们是**女子数据库**的球员，而参照导出只包含**男子数据库**——
上游 FMSuperScout 按"数据库选择"过滤掉另一半（`Dumper` 里的 `PERO_GENDER` 0x10 位判断）。
不是姓名读错、不是出生日期读错，也不是重名。

| 分类 | 数量 | 判定依据 |
| --- | --- | --- |
| 姓名不一致（NameMismatch） | **0** | 若同出生年有人、但姓名都对不上，才会落这一类 |
| 出生日期不一致（BirthMismatch） | **0** | 同名球员在导出中出生年不同才会落这一类 |
| 缺少出生日期（MissingBirth） | **0** | 出生年解码为 0 才会落这一类 |
| 重名/身份冲突（Duplicate） | **0** | 导出里同名多条才会落这一类 |
| 一侧不存在（OnlyOneSide） | **33** | 性别位为女（`PERO_GENDER & 0x10`），导出按性别过滤，天然没有这些记录 |
| 其他（Other） | **0** | 姓名为空等 |
| **合计** | **33** | 抽样 400，配对 367，未匹配 33 |

## 3. 为什么不是"姓名读取错误"

三条独立证据：

1. **性别位**：同一批对象读出的 `PERO_GENDER`（偏移 `person+0x19`）含 `0x10` 位，上游把它定义为女性；
2. **男子样本无此现象**：367 条配对成功的记录里，CA/PA/身高/出生年/合同到期/俱乐部全部一致（见
   `docs/acceptance/LIVE-2026-11-19.md`），说明姓名与出生日期偏移没有整体错位；
3. **导出侧确认**：`dump.json` 的 `meta` 没有性别字段，但导出里 `Jonna Andersson`、`Melissa Barbieri`
   一个都不存在，而同期男球员（如 `Keisuke Honda`）都在。

## 4. 匹配算法（本次使用的、也是唯一的规则）

```
键 = 姓名（原样，大小写不敏感） + "|" + 出生年（PERO_DOB 解码：年 = raw>>16）
命中 → Matched
未命中时按顺序判定：
  性别为女                          → OnlyOneSide（参照只含男子库）
  同名记录 > 1 条                   → Duplicate（身份冲突）
  同名记录 = 1 条但出生年不同        → BirthMismatch
  同出生年有人但姓名都不同           → NameMismatch
  同出生年也没人                     → OnlyOneSide
  姓名为空                            → Other
  出生年 = 0                          → MissingBirth（不参与配对）
```

规则里没有任何"模糊匹配"「按 ID 猜」或"丢弃"的步骤：`MatchDiagnostics.Summarize` 会保留每一条未匹配记录
（测试 `匹配诊断：汇总保留全部未匹配记录` 固定了这一点）。

## 5. 这 33 条对字段验证的影响

- **不能**因此把 27.1 布局判为错误：它们不是读错，而是参照集不含这一半数据库；
- **也不能**因此把 27.1 判为通过：女子数据库对象在合同/球队链上的表现与男子不同
  （抽样里 8/32 的合同指针不可解析，与女子对象数量吻合），这一点**尚未验证**；
- 因此报告里新增独立探测 `women_database`，状态固定为 `Inconclusive`，不参与"通过"计数，
  但会阻止整体状态变成 `Verified`。

## 6. 后续建议（按优先级）

1. **补一份女子数据库参照**：用同一构建、同一存档，让 FMSuperScout 把"数据库选择"切到女子库再导一次，
   或直接以本读取器的女子分部导出为参照（但那会变成自我参照，只能做一致性检查，不能当独立标准）；
2. **在验证样本里保留女球员**（当前 30 人清单已包含 `Chloe Ankers`、`Catriona McFadden`），
   用游戏界面核对她们的俱乐部/位置/国籍——这是目前唯一能独立确认女子库结构的方式；
3. 在 `MatchDiagnostics.Reference` 增加"性别"维度后，报告可以直接给出"男子 367/367、女子 0/33（参照缺失）"，
   而不是笼统的"33 条未匹配"。
