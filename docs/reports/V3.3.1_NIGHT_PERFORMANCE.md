# V3.3.1 NIGHT COMPLETE · 性能基准与优化报告

## 1. 方法与边界

- 运行环境：Windows 11、Python 3.13、SQLite 文件库、本地 SSD。
- 数据：`backend/scripts/bench_v331.py` 生成的**合成数据**（3000 名球员 / 1000 笔转会 / 120 个关注项），名字为 `Bench Player N`，**不代表真实 FM27 存档**。
- 每个场景取 3 次独立会话的中位数，单位毫秒。
- 只做有证据的优化；不重写业务模块、不改变数据正确性、不引入新依赖。

复现命令：

```powershell
cd backend
$env:PYTHONPATH="."
python -m scripts.bench_v331 --players 3000 --transfers 1000
```

## 4. 查询计划证据

```
watchlist_by_save:
  SEARCH w USING INDEX ix_watchlists_fm_save_id (fm_save_id=?)
  SEARCH wi USING INDEX ix_watchlist_items_watchlist_id (watchlist_id=?)

players_by_name:
  SCAN players
```

- 关注名单按存档筛选使用既有索引；本次新增的 `(watchlist_id,status)` 只服务于名单内状态筛选，不改变旧表结构。
- 球员姓名搜索当前是 `%关键词%` 子串匹配，B-tree 索引无法利用，计划中为 `SCAN players`。在 3000 人规模下 27.84 ms，可接受；**结论：不贸然改索引或语法**。若真实存档达到数万人，建议后续评估 SQLite FTS5，而不是把子串匹配改成前缀匹配（会改变搜索语义）。

## 5. 前端性能核对（代码审查，无需改动的部分）

| 项 | 现状 |
|---|---|
| 路由按需加载 | 所有页面为动态 import，构建产物按页面分块（PlayerDetail 35 KB、Squad 25 KB 等） |
| 搜索防抖 | 球员中心已有防抖；本次关注名单新增 300 ms 防抖 |
| 旧请求取消 | 球员中心已有请求序号；本次球员详情页新增 `activeToken`，快速切换球员时旧响应不写入页面 |
| 图表生命周期 | `EChart.vue` 只 init 一次、`dispose` 于卸载、`ResizeObserver` 监听容器；不随无关状态重建 |
| 关注名单渲染 | 搜索结果与名单分组同一次请求返回，避免二次往返 |

## 6. 真实 FM27 数据实测（2026-11-27）

环境：FM27 App `4530370` / build `26620374` / 插件 `27.1`，实时读取 47,523 名球员、47 家俱乐部；合并进存档后共 **62,229 名球员 / 195,893 条快照**。下表为同一真实数据库上的 3 次中位数。

| 场景 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 关注名单（1 项） | 618 ms | **10 ms** | 第二轮优化：`latest_snapshot_subquery` 只聚合被关注实例，不再扫描全部快照；−98.4% |
| 表现分析（演示存档 92 人） | 107,229 ms | **667 ms** | 同位置样本与俱乐部改为一次预取，消除 278 次逐球员查询；−99.4% |
| 球员列表第 1 页 | — | 1,175 ms | 62k 人 + 195k 快照的「每人最新快照」聚合 |
| 球员姓名搜索 | — | 1,191 ms | `%关键词%` 全表扫描 |
| 球员详情 | — | 9 ms | 单实例索引查询 |
| 阵容分析 overview | — | 736 ms | 含位置深度、年龄/工资/合同结构 |
| 引援搜索（ST，20 条） | — | 2,139 ms | 全库前锋评分与排序 |

导入实测：

| 操作 | 结果 |
|---|---|
| 首次导入（55.7 MB JSON） | PASS，589 s；创建 7,647 / 更新 39,864 名球员，新增 47,523 条快照，0 拒绝 |
| 重复导入同一扫描 | `duplicate=true`，8.6 s 幂等返回，不新增快照 |
| 导入后关注项 | 备注、状态、名单均保留 |

结论：本轮两项优化（N+1 消除、关注项快照范围收窄）在真实数据上收益显著；球员列表/引援搜索的耗时主要来自「最新快照」全量聚合，属已知结构成本。后续若要继续优化，建议评估「在 PlayerInstance 上物化 latest_snapshot_id」或 FTS5，而不是在当前阶段扩大改动面（NOT_RUN）。

## 7. 未做与原因

- 未做全站缓存层：现有查询已在几十毫秒级，增加缓存会引入存档切换失效风险，收益不足。
- 未改数据库结构（除新增状态列与索引）：无查询证据支持其他变更。
- 未引入虚拟列表：现有分页已限制渲染数量；真实大数据量下的滚动性能标记为 **NOT_RUN**，等待真实 FM27 存档验证。
