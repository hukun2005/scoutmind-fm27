# V3.2.4 游戏日期根因报告（SM-131）

日期：2026-11-24 · 环境：FM 27.1.0 / build 26620374 / 插件 27.1.0+2505117 / 布局 FM27_1

## 1. 现状

| 来源 | 结果 |
| --- | --- |
| 读取器 `date --json` | `state=DateUnavailable`，`errorCode=date_offset_not_verified` |
| 扫描报文 `scan.gameDate` | 有值（本次 2026-10-23；11-23 的扫描为 2026-07-28） |
| 上游 dump `meta.gameDateSource` | `"memory"` |

## 2. 上游日期到底来自哪里

`third_party/FMSuperScout/src/Dumper.cs` 的 `FindGameDate`：

1. 通过经理链找到“我的球队” `DiagMyTeam`；
2. 读 `team + TEAM_SCHEDULE → SCHED_NEXT_MATCH`（备用 `SCHED_NEXT_MATCH_ALT`）；
3. 用 `DecodeFmDate`（高 16 位年、低 9 位年内序日）解码；
4. 年份必须落在 `GameYear ± 1` 内，否则放弃；
5. 同时用各球队的“下一场比赛”投票做交叉校验（`DateVotes`）。

因此报文里的 `gameDate` 是**“下一场比赛日期”**，不是“当前游戏日期”。它与真实日期最多差到下一轮
赛程（通常数天，国际比赛日/赛季末可能更久）。

## 3. 证据

- 2026-11-23 22:00 扫描：`gameDate=2026-07-28`。
- 2026-11-24 15:39 扫描：`gameDate=2026-10-23`（同一存档、期间用户在正常游玩推进）。
- 两次都来自同一个 `SCHED_NEXT_MATCH` 字段；数值随游戏推进而变，说明它确实是内存里的真实赛程日期。
- 读取器自带的 `date` 探测不含该偏移，且布局里没有经过验证的“当前日期”字段，所以它拒绝猜测——
  这是设计约束，不是缺陷。

## 4. 结论

**`next_match_date` 不能当作当前游戏日期使用。** 任务书第 8.2 条明确禁止这种替代；
把 `upstream_dump + SCHED_NEXT_MATCH` 标成 `verified` 会直接违反“没有经过真实内存读取验证的日期字段，
不得标记为正式可信来源”。

因此 SM-131 的“自动日期变化 → 自动快照”仍然 **BLOCKED**，本轮不启用：
- 已导入数据的 `game_date` 来自赛程日期，只能标 `source=upstream_dump`、`confidence=unverified`；
- 历史快照按“扫描日期不同”自然形成，但不能据此宣称“日期变化检测已验证”；
- `date_source/date_confidence/date_read_status` 模型、同日幂等、倒退保护已经就绪，等可信字段接入即可用。

## 5. 下一步（需要真实内存布局工作）

1. 找到一个“当前游戏日期”字段：候选是主界面/HUD 或全局状态对象里的日期，而不是球队赛程。
2. 在至少两个不同游戏日期上做独立核对（推进前后各读一次，与游戏界面显示对比）。
3. 把该偏移加入 `FM27_1` 布局，标 `Verified`，并在 `FmDateProbe` 中启用。
4. 启用后再打开“日期变化 → 自动快照”，并按任务书做同日幂等与倒退保护的真实验收。

在完成上述步骤前，任何“自动历史快照已完成”的表述都不成立。
