说明：

- 优化前 `recommend` 在真实存档上直接抛 `sqlite3.OperationalError: too many SQL variables`（一次 `IN` 传入 6 万个 player id），所以引援页在该存档不可用；V3.3.2 修复后可用。
- 引援推荐的「无筛选全池」是最坏情况：需要对 6.2 万名球员逐一计算六维评分。真实页面与 AI 足球总监都按位置过滤，`slot=ST` 首次约 4.0 秒；同一存档同一条件下第二次起走缓存。
- 阵容统计冷态只提升约 3%，因为首次仍需完整计算；缓存命中后为亚毫秒级。
- 数值为 3 次中位数，含 FastAPI/Pydantic 序列化之外的纯服务层调用；SQLite 单机文件数据库。

## 2. 根因与改动

### 2.1 最新快照引用（migration `b8f3d2a6c1e9`）

原实现每次列表/搜索/阵容都对全部历史快照做 `GROUP BY player_instance_id, MAX(observed_at)`，真实存档 19.5 万条快照重复聚合。

- 新增 `player_instances.latest_snapshot_id`：导入器写入快照后按真实 `observed_at` 维护；历史回补不会覆盖更新数据；重复快照会补齐空引用。
- migration 按 `(observed_at DESC, id DESC)` 回填 112,686 个实例（两个存档全部实例，回填后 `null_ref_with_snapshots = 0`）。
- 读取端 `latest_snapshot_subquery` 改为：有引用走主键 JOIN；引用为空的历史行回退到原聚合，因此旧库与直接写入快照的测试库行为不变。
- 新增索引：`player_instances(fm_save_id, club_id)`、`(fm_save_id, position)`、`watchlist_items(player_instance_id)`、`transfer_history(fm_save_id, player_name)`。

### 2.2 引援推荐的两处真实缺陷

1. 每名候选都调用一次 `player_score`，而 `player_score` 每次都重建一次六维评分上下文 → O(N²)。改为构建一次 `ScoreContext`，再逐候选 `_score_candidate`，结果口径不变。
2. 一次 `IN` 传入全部 6 万个 player id 查询国籍 → 超过 SQLite 变量上限。改为仅在按国籍筛选时加载，并按 500 个一批；俱乐部直接取候选自身的 `club_id`，去掉逐人查询。
3. 额外优化：`candidate_pool(load_attributes=False)` 先只取快照与统计，位置/年龄/预算过滤后再批量加载命中球员的属性（每批 500），避免为 6 万人加载约 250 万条属性值。

### 2.3 存档级查询缓存

`app/services/query_cache.py`：

- 键：`save_id + data_revision + 逻辑名 + 参数`；`data_revision` = 最大快照 ID、最大实例 ID、最大转会 ID、战术模板最后更新时间。
- 命中：覆盖度、阵容统计、引援评分；TTL 60 秒；导入/战术模板变化立即换版本号。
- 不缓存：球员详情、关注项、备注等即时数据。
- 测试环境每个用例前清空；不同存档键隔离。

## 3. 一致性与回滚

- 最新快照引用只增不删历史快照；历史快照、属性值、原始字段未修改。
- `latest_snapshot_subquery` 对旧数据保留聚合回退，V3.3.1 数据不需要立即重导。
- migration 仅新增列/索引；`downgrade` 删除这些新增对象，不触碰业务数据。
- migration 往返测试覆盖：升级后回填正确、降级后快照数量不变。
- 缓存按数据版本自动失效；进程重启即清空。

## 4. 未做与限制

- 未建立 FTS5 全文索引：中文姓名与位置代码以 `LIKE` + 精确/前缀排序即可满足当前数据量（搜索 118–201 ms）；FTS5 需要额外的分词与一致性维护，本轮不引入。
- 无筛选的全池引援推荐仍需 ~19.5 秒（6.2 万人 × 六维评分）。界面与 AI 总监均按位置过滤，实际路径为 ~4 秒或缓存命中；若未来需要无筛选全池，应改为分批/异步任务。
- 缓存为单进程内存缓存；多进程部署时各自持有，不影响正确性，只是命中率下降。
