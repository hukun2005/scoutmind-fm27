# V3.3.2-05 性能报告

- 环境：Windows 11，本机 SQLite，Python 3.13，Node 20+；数据库为真实存档副本 `v332_05_radar.db`（存档 2，62,229 人，约 1.28 GB）
- 方法：直接调用服务层计时（`time.time()` 包裹单次调用），接口计时用已启动的 FastAPI 实例

## 1. 扫描性能

| 场景 | 处理人数 | 生成/更新 | 耗时 |
|---|---|---|---|
| 首次全量扫描 | 62,229 | 新增 35,086 机会 + 35,086 事件 + 200 提醒 | 18.7 s |
| 重复全量扫描（无变化） | 62,229 | 更新 35,086，事件 0，提醒 0 | 9.9 s |

- 首次慢主要来自 35k 行插入与事件写入；重复扫描只更新字段，无新事件。
- 扫描为同步调用，结果直接返回 `scanned_players/created/updated/deactivated/events/alerts_created`，便于统计。

## 2. 读取性能

| 接口 | 耗时 | 说明 |
|---|---|---|
| `GET /opportunities/summary` | 0.23 s | 统计计数 + 能力说明 + Top 8 |
| `GET /opportunities?limit=5` | 0.10 s | 主机会 JOIN 快照/球员/俱乐部，分页 |
| `GET /opportunities?type=loan_listed` | <0.1 s | 类型索引 `(fm_save_id, opportunity_type, active)` |
| `GET /strategy-cases`（真实存档） | <0.05 s | 无案例直接返回 |

索引：`(fm_save_id, is_primary, active)` 支撑默认列表；`(fm_save_id, overall_score)` 支撑排序；`(fm_save_id, player_instance_id)` 支撑详情与去重。

## 3. 前端性能

- `npm run build`（vue-tsc + vite build）：14.71 s，通过（TransferDirectorView 产物 43.95 kB / gzip 11.84 kB）。
- Playwright 全量 42 个用例：40.2 s，全部通过（本模块 10 个）。
- 雷达页首次打开需等待一次扫描（真实存档约 19 s），页面有 loading 状态；后续读取为 0.1–0.3 s。

## 4. 容量

| 数据 | 行数 |
|---|---|
| `transfer_opportunities` | 35,086 |
| `transfer_opportunity_events` | 35,086（首轮） |
| `alerts`（转会） | 200 |

重复扫描不会增长事件和提醒，长期运行只会在状态真实变化时增长。

## 5. 风险与改进

- 首次扫描 19 s 对桌面端可接受，但若球员数继续增长，建议改为后台任务 + 进度轮询；本轮未实现任务队列，如实标注为限制。
- 内存占用未做峰值采样，本轮未给出数值，不使用估算值冒充实测。
- 合同到期机会占 30,122 条，是列表总量主因；若只需关注近期到期，可在前端默认筛选 6/12 个月桶。
