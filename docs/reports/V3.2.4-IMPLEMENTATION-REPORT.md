## 2. SM-130：真实 Unresolved 链路

### 2.1 根因

上游 dump 只导出“有身份”的球员，哨兵对象被丢弃；读取器此前只消费 dump，所以真实扫描永远看不到
无 UID 球员（V3.2.2.8/V3.2.3 的 0 条不是系统能力问题，而是数据源缺口）。

### 2.2 实现

- 新增 `UnresolvedObjectCollector`：扫描完成后，读取器用 vtable 枚举球员对象，读取 `OBJ_DUNI`；
  哨兵（`0xFFFFFFFF`）与零值对象作为 unresolved 观察追加到报文；
  读取姓名、CA/PA、生日；没有姓名的对象只计数告警，不编造姓名。
- 报文行携带 `identity.kind=unresolved`、`uid_status`、`raw_uid`、`reason`、
  `source_record_id=reader_object:player:<序号>` 与证据；**不写对象地址**。
- 引擎把补齐行数计入 `players`，并写入“对象枚举：N 个球员对象中 M 个没有可用 UID”的告警。

## 3. SM-133：合同字段

- 根因：5/22 抽样合同的到期日解码为 **1900 年**（`0x076C0002 -> y1900 d2`），这是 FM 的占位纪元
  （“没有到期日”），此前被归类为“年份异常”，把空合同当成了读取失败。
- 修复：`ContractDateDiagnostics` 新增 `NoExpiry` 类别；`ObjectProbes.ProbeContracts` 把 1900 与 0
  一样按空合同排除出到期日分母；没有降低任何阈值，没有过滤真实失败。
- 真实复测（同一布局、同一进程）：`expiry_range 17/17 = 100%`、`expiry_after_birth 17/17 = 100%`、
  `contract` 探测整体 **Passed**（此前 Failed）。
- 测试：新增“1900 按空合同排除”“1900 归为 NoExpiry 且不拉低可解码比例”两例。

## 4. SM-132：为什么没有实现 Worker

现有实现已经具备：导入移出事件循环、`GET /imports` 查询、`409 import_in_progress`、启动恢复、
Agent 超时后核验。缺少的是 202 + 持久化 worker + 行级进度 + 取消/重试。

没有在本次硬做的原因：

1. **进度与原子性冲突**：现有导入在单个事务里完成，行级进度无法从另一个连接写入（SQLite 写锁），
   要真进度就得改成批量提交，这会改变“失败不留半份数据”的保证，需要重新设计恢复语义。
2. **任务书要求“先审查已有任务框架，不得增加重复队列”**：项目里没有现成的持久化队列，
   最小可靠的实现需要新表 + 租约 + 心跳 + 取消 + 重试 + 恢复，属于一次独立的架构变更，
   不适合在真实验收后仓促并入。
3. 不做半成品：一个只在测试里 202、真实环境仍同步的“假 worker”比不做更危险。

结论：SM-132 记为 **NOT_RUN**，并保留现有缓解措施。建议下一阶段单独开分支实现
（`import_job_progress` 表 + 批量提交 + 租约 + worker 心跳），再补前端进度页。
