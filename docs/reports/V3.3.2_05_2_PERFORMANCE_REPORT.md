## 2. 优化点与验证方式

### 2.1 分批 + 键集分页

`scan_batched` 以 `PlayerInstance.id > last_id ORDER BY id LIMIT 500` 逐批读取，每批提交一次：

- 不再一次性物化全存档 ORM 对象（旧 `_scan_rows` 会一次取回全部实例/快照/球员）；
- 单批失败只影响当前批；已完成批次保留（取消/异常时可以安全停在中途）；
- 进度、取消、检查点都以“批”为粒度，读取数据库的独立 SELECT 次数与规模线性相关。

### 2.2 每批只取必要关联数据

| 数据 | 旧行为 | 新行为 |
|---|---|---|
| 可用状态 | 全存档窗口函数 | `WHERE player_instance_id IN (当前批)` |
| 已有机会 | 全存档 `TransferOpportunity` | 仅当前批球员 |
| 球员姓名 | 全存档字典 | 仅当前批 |
| 俱乐部均值 | Python 遍历全部行 | SQL `GROUP BY club_id HAVING count >= 5`，每次扫描一次 |
| 历史快照 | 全量关联 | 只用 `latest_snapshot_id` |

### 2.3 增量扫描

变化条件（任一）：

- 最新快照 `imported_at > since_time`；
- `player_instances.club_linked_at > since_time`；
- `player_instances.created_at > since_time`。

`since_time` 取最近一次成功扫描的 `finished_at`，不取“当前时间”作为伪变化标识；没有可用标识时退回全量并显式标注。真实数据实测：无变化时 0.208 秒完成。

### 2.4 安全下线与 `scan_token`

- 全量扫描每行写入 `scan_token = task_id`；**全部批次成功结束后**才把 `active=True AND scan_token != 当前` 的机会分批下线；
- 取消/失败时不下线旧机会，避免“半扫描导致机会消失”；
- 增量扫描只对本次处理过的球员下线旧机会，不影响未变化数据。

### 2.5 索引

本版本**没有新增业务字段索引**，因为现有索引已覆盖关键路径：

- `player_instances.fm_save_id`、`player_instances.club_id`、`player_instances.latest_snapshot_id` 已有索引；
- `transfer_opportunities (fm_save_id, overall_score)`、`(fm_save_id, player_instance_id)` 已存在；
- 新增 `transfer_opportunities (fm_save_id, scan_token)`，用于安全下线的批量筛选；
- 新增 `background_tasks (fm_save_id, status)`、`(task_type, status)` 与活跃锁部分唯一索引。

没有为了“看起来优化”而给低区分度字段加索引。

## 4. 限制

- 真实数据的“首次全量扫描”在已扫描过的副本上测得 6.4 秒；冷启动（首次建库、无缓存）会略慢，但批次耗时上限仍在亚秒级。
- 合成数据的机会密度高于真实数据，吞吐仅供参考，不代表所有存档。
- 未对旧同步实现做同机对比测量，因此报告只陈述当前实测值，不宣称“提升了 N 倍”。
