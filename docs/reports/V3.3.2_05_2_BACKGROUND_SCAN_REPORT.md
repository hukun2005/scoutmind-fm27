## 2. 数据模型

`background_tasks` 关键字段：

| 字段 | 说明 |
|---|---|
| `task_id` | UUID，唯一；同时作为本次扫描的 `scan_token` |
| `fm_save_id` / `task_type` / `lock_key` | 存档、任务类型、并发锁粒度（`scan` / `club_link`） |
| `status` | `PENDING` / `RUNNING` / `CANCELLING` / `CANCELLED` / `COMPLETED` / `PARTIAL` / `FAILED` |
| `progress` / `total` / `processed` / `matched` / `failed` | 前端进度与结果计数 |
| `checkpoint_json` | `last_instance_id` / `token` / `mode` / `processed`，用于续跑 |
| `result_json` | 扫描/修复结果摘要 |
| `started_at` / `finished_at` / `heartbeat_at` / `cancel_requested_at` | 生命周期观测 |
| `error_code` / `error_message` | 稳定错误码 + 面向用户的简短文案 |
| `attempt_count` | 有限重试计数 |

并发兜底（migration 中创建）：

```sql
CREATE UNIQUE INDEX uq_background_task_active_lock
ON background_tasks (fm_save_id, lock_key)
WHERE status IN ('PENDING','RUNNING','CANCELLING');
```

即使多个请求同时创建任务，数据库也只允许一个活跃任务；应用层捕获 `IntegrityError` 后返回已存在的任务（`reused=true`）。

## 3. 执行流程

```text
POST /transfer-director/scans
  → create_task(): 查活跃任务（有则复用）→ 插入 PENDING → 提交线程池 → 202
  → _run_task()
      RUNNING + started_at + attempt_count+1
      FULL_SCAN / INCREMENTAL_SCAN / RECOVERY_SCAN → transfer_radar.scan_batched()
        每批：计算 → 写回 → commit → progress_cb() 更新进度/心跳/检查点
      CLUB_LINK_REPAIR → club_linkage.repair()（分批、幂等）
      成功 → COMPLETED（failed>0 时 PARTIAL）→ progress=100 → result_json
```

任务类型：

- `FULL_SCAN`：完整分批扫描；
- `INCREMENTAL_SCAN`：以最近一次成功扫描的 `finished_at` 为变化标识；**没有可靠标识时退回全量**，并在 `result.incremental_available=false`、`error_code=incremental_fallback_full` 明确标注；
- `RECOVERY_SCAN`：与全量共用锁，用于恢复；
- `CLUB_LINK_REPAIR`：关联修复。

## 4. 取消、超时、重试与恢复

- **取消**：`cancel_task` 幂等；`CANCELLING` 后执行器在**下一批开始前**停止并抛出 `ScanCancelled`；已提交批次保留；`checkpoint_json` 记录 `last_instance_id`，`progress` 按已处理比例保留。
- **超时**：`settings.scan_task_timeout_seconds`（默认 1800 秒），超时标记 `FAILED / task_timeout`。
- **有限重试**：`OperationalError`（数据库忙）在 `attempt_count < settings.scan_max_attempts` 时回到 `PENDING` 并重新提交；超过后 `FAILED / database_busy`。不会无限重试。
- **重启恢复**：`recover()` 在应用启动时执行：
  - `CANCELLING` → `CANCELLED`；
  - 有检查点（或关联修复）→ `PENDING` 并重新提交；
  - 其他 `RUNNING/PENDING` → `PARTIAL / app_restart`，绝不永久占用活跃锁。
- **应用关闭**：`shutdown_executor()` 把 `RUNNING` 标记为 `PARTIAL / app_shutdown` 并关闭线程池。

## 5. 用户可见提示

`serialize()` 只返回稳定字段，不暴露堆栈或 SQL。状态文案：

| 状态 | 文案 |
|---|---|
| `PENDING` | 扫描任务已排队 |
| `RUNNING` | 正在更新转会情报 |
| `CANCELLING` | 正在取消扫描 |
| `CANCELLED` | 扫描已取消 |
| `COMPLETED` | 转会情报更新完成 |
| `PARTIAL` | 本次更新只完成了部分数据处理，现有数据不会被删除 |
| `FAILED` | 本次转会情报更新未能完成，系统可以安全重试 |

`internal_error` 只写日志，`error_message` 使用固定安全文案。

## 9. 限制

- 执行器是**单进程内存线程池**，与本地单机桌面应用一致；同一数据库被多个独立进程同时写入不在支持范围内（SQLite 本地应用本身也不支持）。
- 进程被强制杀死时无法执行关闭钩子；下次启动由 `recover()` 标记 `PARTIAL` 或按检查点续跑，不会留下永久 `RUNNING`。
