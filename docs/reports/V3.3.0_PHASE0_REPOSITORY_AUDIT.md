## 2. 已存在的导入能力

### 2.1 统一扫描导入（核心）

- 入口：`POST /api/v1/imports/scan`（`backend/app/api/routes_core.py:599`）
  - 接受 JSON / NDJSON 请求体，或 multipart `file` 字段；统一经 `read_request_payload` 限流、限大小。
  - 对 FMSuperScout dump 先经 `maybe_adapt`（`routes_adapters.py:312`）转换为标准 scan payload。
- 解析：`backend/app/ingestion/protocol.py`
  - `parse_payload` 支持单对象 JSON 与 NDJSON（首行 header）。
  - `schema_version` 主版本必须为 1，否则 `ProtocolError`。
  - `scan_id` 是严格安全字符集（无路径分隔符、无 `..`）。
- 写入：`backend/app/ingestion/importer.py` `ScanImporter`
  - `(fm_save_id, scan_id)` 唯一约束 = 幂等键；`operation_id` 作为更强操作幂等键。
  - 单事务写入；异常 `rollback` 并落 `failed`；取消状态机 `queued → cancelled`、`running → cancel_requested → cancelled`。
  - `WriteFence` 代次校验（存档切换后旧任务整体作废）；`recover_interrupted_imports` 启动恢复。
  - 每行拒绝写入 `import_rows`（稳定 code + message），部分成功为 `status=partial`。
- 身份匹配：`backend/app/ingestion/identity.py` `resolve_player_instance`
  - 优先 `save_local_uid`；UID 复用通过生日不一致检测并保留两个身份；姓名单独不作为合并依据。
  - 缺稳定 ID 的行进入 `unresolved` 候选（`ingestion/unresolved.py`）。
- 来源适配：
  - FMSuperScout：`ingestion/adapters/fmscout.py`、`api/routes_adapters.py`。
  - 历史转会：`POST /api/v1/imports/transfers/history`（`routes_transfer_history.py`）。
  - 阵容 CSV：`POST /api/v1/imports/squad-csv`（`routes_core.py:319`）。
  - 转会独立导入：`POST /api/v1/imports/transfers`（`routes_core.py:256`）。

## 3. 当前缺失能力（本版本要补齐）

1. **没有统一的数据中心入口**：扫描、FMSuperScout、阵容 CSV、历史转会各自独立，用户必须知道该点哪一个。
2. **没有统一的来源/格式/版本自动识别**：`maybe_adapt` 只识别 FMSuperScout dump；CSV 与 NDJSON 需要用户自己选入口。
3. **没有导入前的确定性修复引擎**：`quality/rules.py` 只做只读诊断；`quality/dedup.py` 在导入后评估。
   缺少：空白清理、日期格式转换、数值字符串转换、枚举标准化、完全重复行去除、旧字段名映射。
4. **没有修复审计表**：修复前值/后值/规则/规则版本/来源/执行时间/结果无法按批次追溯。
5. **没有批次级 Level 3 隔离记录**：非法行会写入 `import_rows`，但没有面向用户的“隔离数量/待确认”聚合视图。
6. **没有数据中心状态 API**：没有一次返回“游戏是否运行、存档是否识别、可同步性、记录数、最近同步、健康状态”的接口。
7. **后端没有游戏进程检测**：识别 `fm.exe` 只在 C# 读取器内（`live-reader/ScoutMind.Reader/ProcessDetector.cs`），后端无法直接回答“FM27 是否运行”。
8. **前端数据中心过于技术化**：`frontend/src/views/DataView.vue` 直接暴露 scan_id、NDJSON、原始报文路径、适配器字段表。
9. **没有 6 阶段导入进度与统一结果页**：前端只能看到最终结果。

## 5. 潜在兼容性风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 破坏现有导入契约 | `/imports/scan` 被 Reader、Agent、测试大量使用 | 只新增入口；`/imports/scan` 行为不变 |
| 幂等被削弱 | 修复记录重复写入 | 审计按 `(import_job_id, entity, row_index, rule_id)` 去重 |
| 事务边界 | 修复审计与业务写入必须同生共死 | 复用 `ScanImporter` 事务提交，审计在同一 Session 内提交 |
| SQLite 锁表 | 导入并发已限流（`import_slot`） | 新入口复用同一信号量 |
| 大批量性能 | 44k 球员导入 | 修复只做 O(n) 处理；批量查询去重；不做 N+1 |
| 存档隔离 | 错误存档写入 | 复用 `get_active_save` + WriteFence；检测到存档不明确时不写入 |
| 身份生命周期 | 自动修复绕过审核 | 只使用稳定 UID；不把 Pending 改 Verified；不按姓名合并 |
| 迁移安全 | 新增表 | 只新增表与索引，不修改历史 migration |

## 6. 建议实施顺序

1. Phase 1：架构与测试计划文档（`docs/architecture/AUTOMATIC_DATA_IMPORT_ENGINE.md`）。
2. Phase 2：`validation.py` + `repair.py` + `DataRepairAudit` + migration + 单元测试。
3. Phase 3：身份/去重接入（复用 `resolve_player_instance`、`dedup.build_canonicals` 的只读摘要）。
4. Phase 4：`engine.py` + `routes_datahub.py` + 事务、幂等、回滚、并发测试。
5. Phase 5：前端三区域 + 进度 + 结果页，技术诊断折叠。
6. Phase 6：针对性 pytest、前端 build、回归。
7. Phase 7：真实 FM27 验收（不可用则 `NOT_RUN`）。
8. Phase 8：README / CHANGELOG / 文档 / 最终报告 / PR。

## 7. 结论

现有导入链路已具备事务、幂等、身份匹配、去重与审计的基础，**不需要重写**。
V3.3.0 的增量集中在一层新的编排与治理层（`app/datahub`）、一张修复审计表、三个新 API 和一次数据中心 UI 简化。
