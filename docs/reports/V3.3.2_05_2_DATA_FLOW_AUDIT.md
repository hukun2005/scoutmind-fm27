## 2. 核心问题：172 个俱乐部关联的根因

### 2.1 结论

**根因是数据源本身没有提供俱乐部字段，不是 Reader 映射错误，也不是 Importer 丢字段。**

证据链：

1. 上游 FMSuperScout dump 的 `coverage`：`teams=false`、`loans=false`、`ownership=false`、`transfers=false`；`clubs` 只有俱乐部对象列表，不含球员归属。
2. Reader 输出 dump 中 47,523 名球员：
   - 含 `club` 字段：**0**
   - 含 `club_uid` 字段：**75**
   - 原始 dump `warnings` 明确写入：**“47448 名球员没有俱乐部名称：保持为未知，不归入任何俱乐部。”**
3. Reader 映射代码 `live-reader/ScoutMind.FMReader/Integration/UpstreamDumpMapper.cs:275-295`：只有 `player["club"]` 非空时才生成 `club_uid`；为空时 `PlayersWithoutClub++`，不写入任何俱乐部引用。
4. Importer `backend/app/ingestion/importer.py:791-794`：只使用 `record.club_uid`，为空时不写 `club_id`；`importer.py:737-755` 明确注释“never a guessed club”。
5. 数据库校验：
   - `player_instances` 中 `club_id` 非空 = **172**
   - `club_id` 指向不存在或跨存档俱乐部（INVALID_REFERENCE）= **0**
   - `latest_snapshot.club_id` 非空 = **147**
   - 任一历史快照有 `club_id` 的去重实例 = **172**（与 instance 完全一致）
   - `instance.club_id` 与最新快照 `club_id` 不一致 = **0**
   - 仅靠阵容 CSV 才能关联的实例 = **0**
6. 每次导入的俱乐部覆盖与 dump 完全吻合：

| import_job | 球员数 | 带 club_id 的快照数 |
|---:|---:|---:|
| 4（fmsuperscout） | 1,500 | 103 |
| 6 | 48,116 | 103 |
| 7 | 48,089 | 103 |
| 8 / 9 | 50,365 | 136 |
| 10（当前 dump） | 47,523 | 75 |

结论状态：`MISSING_SOURCE_FIELD`（数据源未提供俱乐部字段），不是 `UNRESOLVED`，也不是 `INVALID_REFERENCE`。

### 2.2 为什么数据库是 172，而最新 dump 只有 75

`player_instances.club_id` 是“曾经观测到过”的并集：早期 dump（50,365 人）有 136 人带 `club_uid`，当前 dump 只有 75 人。最新导入不会清空旧关联（俱乐部归属不会因为一次 dump 缺字段就消失），因此实例并集为 172；最新快照覆盖为 147（25 人的俱乐部只出现在更早的快照里）。

这 172 不是“映射失败”，而是**数据源只有 172 人能提供俱乐部信息，且这 172 人全部成功关联**。

### 2.3 `club_link_rate`

| 口径 | 计算 | 结果 |
|---|---|---:|
| 全局关联率（instance 并集 / 全部球员） | 172 / 62,229 | **0.28%** |
| 最新观测关联率 | 147 / 62,229 | **0.24%** |
| 可验证来源关联率（已关联 / 数据源给出俱乐部的球员） | 172 / 172 | **100%** |
| 最新 dump 字段覆盖率 | 75 / 47,523 | **0.16%** |
| 机会中带有效俱乐部的比例 | 102 / 35,086 | **0.29%** |

> 不建议把 172/62,229 当作“修复目标”。真正可提升的唯一合法途径是用户导入阵容 CSV（明确的俱乐部列）或上游提供 team 字段；不得用姓名猜测。

### 2.4 状态分类（存档 2）

| 状态 | 数量 | 说明 |
|---|---:|---|
| LINKED | 172 | `club_id` 有效，且俱乐部属于同一存档 |
| INVALID_REFERENCE | 0 | 无悬空/跨存档引用 |
| UNRESOLVED | 0 | 没有“有俱乐部 UID 但解析失败”的记录 |

| NO_CLUB | 0（无法可靠判定） | 当前数据源没有“自由球员/退役”标记，不能把“无字段”当成“无俱乐部” |

### 2.5 机会与俱乐部聚合

| 机会类型 | 总数 | 带有效俱乐部 |
|---|---:|---:|
| listed 已挂牌 | 711 | 0 |
| loan_listed 可租借 | 1,619 | 0 |

因此“按俱乐部筛选挂牌/可租借/解约球员”在当前真实数据上必然接近空结果——这是字段缺失，不是筛选逻辑错误。前端必须明确提示，而不是显示 0 制造误解。

## 3. 发现的问题清单

### 问题 1：数据源缺少俱乐部字段

```
问题位置：FMSuperScout dump → UpstreamDumpMapper.cs:275-295 → importer.py:791-794
根因：上游 coverage.teams=false，47,448/47,523 名球员没有 club 名称；Reader 按设计不猜测。
受影响数据：存档 2 的 62,057 名球员无俱乐部归属；所有 listed/loan/release 机会均无俱乐部。
修复方案：停止自动绑定；健康度接口标记 MISSING_SOURCE_FIELD；提供阵容 CSV / 上游 team 字段两条合法补录路径。
回归测试：test_club_linkage.py::test_missing_source_field_is_reported_not_guessed
```

### 问题 2：阵容 CSV 归属不反写球员俱乐部

```
问题位置：backend/app/ingestion/squad_csv.py:399-437（只写 squad_assignments）
根因：SquadAssignment 与 PlayerInstance.club_id 是两套并列关系，导入后未同步实例归属。
受影响数据：存档 2 有 17 条 squad_csv 归属（均已在 payload 关联中），暂无差异；但新存档仅有 CSV 时会漏关联。
修复方案：CSV 自动关联（confidence>=0.8 且 club_id 有效）后同步回填 instance.club_id，记录来源 squad_csv。
回归测试：test_squad_csv_club_link.py
```

### 问题 3：旧俱乐部关联未记录来源与时间

```
问题位置：backend/app/models.py:192-214（PlayerInstance 只有 club_id）
根因：无法区分 payload_club_uid / squad_csv / backfill，也无法追踪回填批次。
受影响数据：全部 172 条关联。
修复方案：新增 club_link_source、club_linked_at 字段（仅新增 migration），回填时写入来源。
回归测试：test_club_link_repair.py::test_backfill_records_source_and_is_idempotent
```

### 问题 4：俱乐部成员统计使用全部历史快照

```
问题位置：backend/app/clubs/resolver.py:329-341
根因：_member_counts 统计 PlayerSnapshot.club_id 的全部历史行，同一球员多次导入被重复计数。
受影响数据：俱乐部列表的 players 数偏高。
修复方案：改为按当前 PlayerInstance.club_id 统计（或 latest_snapshot_id）。
回归测试：test_club_resolution.py 增补成员计数用例。
```

### 问题 5：扫描一次加载全部球员并逐行写 ORM

```
问题位置：backend/app/services/transfer_radar.py:389-527、158-165
根因：_scan_rows 一次性物化 62,229 个 ORM 对象；写回逐行 add/update；无分批、无进度、不可取消。
受影响数据：全量扫描约 18.7 秒（历史记录），内存峰值随球员数线性增长。
修复方案：分批投影查询 + 批量 upsert + 增量（import_job_id 变化）+ 后台任务。
回归测试：test_transfer_radar_batch.py、bench_transfer_scan.py
```

### 问题 6：扫描是同步 HTTP 请求

```
问题位置：backend/app/api/routes_transfer_director.py:141-146
根因：POST /opportunities/refresh 在请求线程内执行完整扫描。
受影响数据：页面切换/网络中断会丢失进度，无法取消，无法恢复。
修复方案：新增 POST /scans 后台任务（持久化 + 有界执行器），旧接口保留兼容。
回归测试：test_background_scan.py
```

## 4. 安全修复边界（按任务书）

1. **不按姓名绑定球员或俱乐部。**
2. **不把不同存档的相同 UID 视为同一实体。**
3. **不为了提升关联率而绑定无法验证的球员。**
4. **不把“没有字段”显示成“自由球员”。**
5. 只修复：悬空引用、可验证 UID 的回填、CSV 已验证归属的同步、来源/时间元数据。
6. 真实 FM27 的全量俱乐部验收在当前数据源下标记：
   - 俱乐部字段覆盖：`MISSING_SOURCE_FIELD`
   - 真实存档俱乐部聚合验收：`BLOCKED_BY_REAL_DATA`
