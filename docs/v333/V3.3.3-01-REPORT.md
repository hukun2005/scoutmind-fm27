### 2.3 Graph 拓扑

```
START
  → validate_scope（用户 / 存档 / save_generation 校验）
  → classify（任务分类）
  → plan（Provider 规划；不可用则规则回退）
  → validate_plan（工具白名单、参数、步数/工具数上限）
  → review_results ─┬─ continue → execute_step → review_results
                    ├─ approval_required → request_approval（interrupt）
                    │        ├─ approve → apply_approved → review_results
                    │        └─ reject  → 安全结束（cancelled）
                    ├─ report_ready → finalize_report → END
                    └─ fail / cancelled → END
```

| `agent_max_tool_calls` | 5 |
| `agent_task_timeout_seconds` | 120 |
| `agent_model_timeout_seconds` | 30 |
| `agent_tool_timeout_seconds` | 10 |
| `agent_max_concurrent_tasks` | 2 |
| `agent_event_buffer` | 200 |
| `agent_approval_ttl_seconds` | 600 |

### 2.4 State

`AgentTaskState` 为 TypedDict，字段与任务书 §6.1 对齐：`task_id / thread_id / user_id / save_id /
save_generation / task_type / user_goal / execution_plan / current_step / completed_steps /
pending_steps / tool_results / analysis_results / approval_requests / approved_actions /
execution_status / error / final_report / step_count / tool_call_count / deadline_epoch / created_at / updated_at`。

`user_id`、`save_id`、`thread_id`、`save_generation` 只由服务端写入；模型计划中的同名参数会被
`ToolAdapter` 直接拒绝（复用 `llm_planner._validate_arguments` 的禁用参数规则）。

### 2.5 双层持久化

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 业务库 | `agent_tasks` / `agent_task_events` / `agent_approvals` | 任务状态、进度、报告、错误、事件、确认单 |
| Checkpoint | 独立 `data/agent_checkpoints.db`（WAL，`busy_timeout=30s`） | Graph State、节点进度、中断上下文 |

两者不相互替代；Checkpoint 与业务连接分离，避免长任务写入与导入事务争抢主库锁。
PostgreSQL 部署下 `build_checkpointer()` 明确返回 `AGENT_CHECKPOINT_UNSUPPORTED`（需要部署层注入
`langgraph-checkpoint-postgres` 连接），不会静默降级到 SQLite。

## 3. 业务工具适配

- 直接复用 `backend/app/agents/tools.py` 的 27 个模型工具（`llm_planner.TOOL_SPECS`）与 31 个内部工具，
  没有重写任何搜索、阵容、转会、报价、俱乐部画像逻辑。
- `ToolAdapter` 统一提供：工具文档、严格参数校验、作用域校验、确认判定、幂等指纹、工具声明。
- 参数校验复用 `validate_tool_arguments` / `assert_tool_scope`（本次在 `llm_planner` 中新增两个公开别名，
  不改变原行为）。
- 写工具：当前只有 `record_negotiation`（`WRITE_TOOLS`）。它必须经过确认，且在同一任务内以
  `工具名 + 规范化参数` 的指纹去重；确认单消费后即使进程重启也不会重复执行。
- 工具失败（参数、越权、执行异常）被记录为步骤错误，不伪造结果；全部失败则任务失败并给出错误码。

## 4. 用户确认（Human-in-the-loop）

流程：`review_results` 判定写操作 → `request_approval` 先落库确认单，再 `interrupt(payload)` →
用户确认/拒绝 → 后端重新校验 → `Command(resume={"decision": ...})` → `apply_approved` 消费确认单并执行。

| 规则 | 实现 |
| --- | --- |
| 一次性 | `status: pending → approved → consumed`，重复确认返回 409 |
| 过期 | TTL 默认 600s；读取/决策时标记 `expired`，确认接口返回 `AGENT_APPROVAL_EXPIRED` |
| 拒绝终态 | `rejected` 不可再批准；任务安全结束为 `cancelled`，不产生副作用 |
| 存档代次 | 确认单绑定创建时的 `save_generation`；与当前 `SaveWriteGate.generation` 不一致即失效 |
| 跨用户/存档 | 决策时重新校验 `user_id` / `fm_save_id`，不匹配返回 403 或 404 |
| 内容不可篡改 | 确认单保存 `payload_hash`；恢复时使用已存确认单，不接受前端传入的操作内容 |
| 恢复幂等 | resume 会重放节点开头；`ensure_pending` 复用同一张单；`apply_approved` 对已消费单跳过执行 |

API 只允许在 `waiting_approval` 状态确认/拒绝，其他状态返回 409，避免对已结束任务重放。

## 5. API 与前端

### 5.1 API

新增 `backend/app/api/routes_agent_tasks.py`，并保持 `/agent/conversations*`、`/agent/director/*` 兼容：

`POST /agent/tasks`、`GET /agent/tasks`、`GET /agent/tasks/{id}`、

Traceback、Graph 内部结构。错误体统一为 `{"error": {"code", "message"}}`，详见 `docs/API.md` §17。

### 5.2 前端

- 新增 `AgentTaskPanel.vue`，嵌入既有 AI 总监页（复用 V4.0 页面，不新建首页）。
