# V3.3.3-02 瓶颈报告（BOTTLENECK-REPORT）

依据：静态代码审计 + `docs/performance/V3.3.3-02-BASELINE.md` 的三档规模基线。
按「影响面 × 实测证据」排序，只列真实存在、可复现的问题。

## B1. 转会位置筛选：整表加载 + `IN` 变量超限（P0，功能性错误）

**位置**：`backend/app/analytics/transfers.py`（`fetch_transfers` / `count_transfers` / `transfer_list_coverage`）

**旧逻辑**：

1. 只要出现 `position_group`，就跳过 `LIMIT/OFFSET`，先 `SELECT` 全部匹配行（含 `selectinload(components)`）；
2. 再用 Python 取 `PlayerInstance.position` 逐行判断分组；
3. `count_transfers` 与 `transfer_list_coverage` 各自再走一遍同样的全量路径。

**后果**：

- 5 万行规模时 `_instance_positions` 生成 `IN (?, ?, …)`，超过 SQLite 绑定变量上限，直接
  `OperationalError: too many SQL variables`（基线 10k/100k/500k 均为 ERROR）。
- 即使不报错，一次列表请求要读 3 次全表（分页、计数、覆盖率），500k 规模下 600+ ms。

## B2. 转会「联赛 + 位置」组合筛选：每页多次全量扫描（P0，最大热点）

**位置**：同上，以及 `backend/app/api/routes_transfers.py::list_transfers`

**旧逻辑**：联赛条件已经能下推到 Club 子查询，但 `needs_python_filter` 一旦为真，分页仍在 Python 侧完成；
`count_transfers`、`transfer_list_coverage` 又各扫一遍。

**实测**：10k 755 ms（69 条 SQL），100k 2140 ms（129 条 SQL），500k 2344 ms。
SQL 条数随总行数/页数增长，说明分页没有真正下推。

## B3. 俱乐部映射：每个请求加载整个存档的俱乐部（P1）

**位置**：`backend/app/analytics/players.py`（`list_players`、`player_profile` 的 `_club_map`）、
`backend/app/api/routes_transfers.py::list_transfers`

**旧逻辑**：`SELECT * FROM clubs WHERE fm_save_id = ?` 全量加载，然后只用到当前页/单个球员的
少数俱乐部。基准数据 500k 球员对应 4000 家俱乐部，于是「球员详情 ×5」在 100k 档就要 191 ms
（每详情加载 4000 行），500k 档 135 ms。俱乐部筛选列表在 100k 档 30.5 ms，其中大部分是无关俱乐部的加载。

## B4. 球员列表计数：UNION ALL 两支全量物化（P1，未完全解决）

**位置**：`backend/app/analytics/players.py::list_players`

`latest_snapshot_subquery()` 把「有 `latest_snapshot_id` 的现代行」与「无引用的历史行」UNION ALL，
`COUNT(*)` 需要把两支全部物化。500k 档单次列表 1017 ms，其中计数与默认排序占主要部分。

**尝试与结论**：本 PR 试过「无历史行时只查现代分支 + 快照 observed_at 索引」，
排序场景可降到约 890 ms，但会让「按俱乐部筛选」从 16 ms 退化到 93 ms（优化器改走
`observed_at` 索引回表）。该方案未保留，详见《OPTIMIZATION-REPORT.md》第 5 节。
这是一个已定位、但仍 **OPEN** 的瓶颈。

## B5. Agent 事件：每条事件一次 `MAX(seq)` + 一次 commit（P1）

**位置**：`backend/app/agent_runtime/events.py::TaskEventBus.append`，
`backend/app/agent_runtime/nodes.py::execute_step`

**旧逻辑**：

- 每条事件先 `SELECT MAX(seq)`，再 INSERT，再 `commit()`；
- 一个工具步骤依次写 `step_started`、`tool_started`、`tool_completed`，共 3 次 commit；
- 50 条事件 = 100 条 SQL、150 ms（CPU 仅 36 ms，约 76% 时间在提交/落盘）。

## B6. Agent 节点写缓存按任务累积、从不释放（P1，内存泄漏）

**位置**：`backend/app/agent_runtime/nodes.py::AgentNodes._write_cache`

`_write_cache` 以 `task_id` 为键保存工具写调用，任务结束后没有清理。
运行时间越长、任务越多，进程内存只增不减；这是长期运行服务端的真实泄漏点。

## B7. 导入：逐球员存在性查询 + 逐快照 flush（P2，本阶段只测量）

**位置**：`backend/app/ingestion/importer.py::_create_snapshot`（`SELECT` 存在性 + `flush()`）

5000 人导入 28.4 s（176 人/秒），SQL 次数与球员数线性相关。批量化需要同时调整
「快照 id 立即用于属性行 / 最新快照引用」的语义，风险高于本阶段收益，**未在本 PR 修改**；
已作为后续项记录，并保留可重复基准。

## B8. 前端 Agent 面板：后台标签页仍轮询（P2）

**位置**：`frontend/src/components/AgentTaskPanel.vue`（2.5 s 定时器）

任务处于运行态时每 2.5 s 拉取 detail + events + approvals。页面切到后台后仍继续请求与重渲染。
本 PR 增加 `document.hidden` 守卫；其余部分（列表防抖、`requestSeq` 丢弃旧请求、卸载清理定时器、
服务端分页）审计后未发现需要修改的问题。
