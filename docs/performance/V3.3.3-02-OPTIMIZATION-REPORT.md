## 1. 转会影响下推（P0）

**文件**：`backend/app/analytics/transfers.py`

新增 `relational_conditions(save_id, filters)`，把两类关联筛选翻译成 SQL：

- **联赛**：`from_club_id IN (保存内该联赛俱乐部) OR to_club_id IN (…)`（沿用原 SQL 子查询）；
- **位置**：`player_instance_id IN (SELECT id FROM player_instances WHERE fm_save_id = ? AND upper(trim(position)) IN (...))`。

分组码来自 `app.ingestion.attributes.POSITION_GROUPS`，与 `position_group()` 同一张表，因此：

- `"AMR, MR"` 这类多码字符串仍然**不属于**任何分组（旧语义保持）；
- `NULL` 位置不匹配任何分组；
- 位置数据源仍是 `PlayerInstance.position`（与旧 Python 路径一致）。

`fetch_transfers` 现在无条件使用 `_with_relational_filters(...)`，`LIMIT/OFFSET` 真正下推；
`count_transfers`、`transfer_list_coverage` 复用同一条件，各用一条 COUNT/聚合查询，
不再「分页扫一遍、计数扫一遍、覆盖率再扫一遍」。

同时把 `_instance_positions` 改为每 500 个 ID 分块查询，消除 `similar_transfers` 在
超大数据集上的潜在变量上限问题，并删除不再使用的 `_position_group_of`。

## 2. 俱乐部按页加载（P1）

- `backend/app/analytics/players.py`：`_club_map` → `_clubs_by_ids`；列表只加载当前页
  `club_id`，详情只加载该球员的俱乐部。
- `backend/app/api/routes_transfers.py::list_transfers`：只加载当前页转出/转入俱乐部。

结果：「球员详情 ×5」100k 档 191 → 24 ms（7.9 倍），500k 档 135 → 28 ms（4.8 倍）；
「按俱乐部筛选」在 10k/100k 档提升约 4 倍。

## 3. 球员列表筛选逻辑去重（可维护性）

`players.py` 把筛选条件抽成 `_apply_player_filters(query, base, filters, save_id)`，
`filtered_players` 与计数共用同一套条件；位置分组码同样改为引用 `POSITION_GROUPS`，
避免列表与搜索两处硬编码漂移。行为不变，由既有测试与新增测试共同锁定。

## 4. Agent 事件：事务内 seq 缓存 + 合并提交（P1）

**`backend/app/agent_runtime/events.py`**

- `append(..., commit: bool = True)` 新增提交开关；
- 同一事务内缓存 `task_id → 已分配 seq`，连续追加只查一次 `MAX(seq)`；
- 在 `Session` 的 `after_commit` / `after_rollback` 上统一清理缓存，
  避免另一个会话/线程写入更高 seq 后复用过旧值（此问题在 `test_cancel_waiting_task` 中被发现并回归验证）。

**`backend/app/agent_runtime/nodes.py`**

- `execute_step` 的 `step_started` 与 `tool_started` 合并为一次提交（`commit=False` + 下一次默认提交），
  每个工具步骤从 3 次 commit 降到 2 次；
- 新增 `AgentNodes.release(task_id)`。

**`backend/app/agent_runtime/runtime.py`**

- 保存 `_nodes` 引用；
- 任务进入终态（completed/failed/cancelled）或 `_mark_failed` 时调用 `release`，修复写缓存泄漏。

注意：直接调用 `TaskEventBus.append`（未使用 `commit=False`）的路径仍是逐条提交，
因此基准中的「事件追加 50 条」保持 150 ms；节点层批量路径为 9.9 ms。两者都在结果文档中如实列出。

## 5. 索引 migration（P1）

新增 `backend/alembic/versions/c4d5e6f7a8b9_v3_3_3_02_performance_indexes.py`
（`down_revision = b8e4d1c7f2a9`）：

| 索引 | 表 | 用途 |
| --- | --- | --- |
| `ix_transfer_save_status_date` | `transfer_history(fm_save_id, status, transfer_date)` | 默认列表：completed + 日期倒序 |
| `ix_transfer_save_status_fee` | `transfer_history(fm_save_id, status, effective_fee)` | 按金额排序 |
| `ix_agent_tasks_save_user_created` | `agent_tasks(fm_save_id, user_id, created_at)` | 任务列表 |

只新增索引，不修改历史 migration；`downgrade` 可完整回退。

**被否决的方案（记录原因）**：曾尝试给 `player_snapshots(observed_at)` 建单列索引，
并让列表在「无历史行」时只查现代分支。实测 500k 行时优化器改为「按 observed_at 扫描再回表过滤」，
`按俱乐部筛选` 从 16 ms 退化到 93 ms，列表收益也不稳定。因此索引与分支都未保留——
这是本阶段唯一一个「测了但主动放弃」的优化，避免用局部收益换取可预测的回归。
